# 开发阶段与个人敏捷原则

最后更新：2026-06-06

## 1. 调整背景

当前项目已经完成 A3 方向确认、基础架构、MVP 学生端闭环、本地运行配置和 Tutor Agent 真实 LLM 最小接入。前期多 Agent、强文档、强状态流转的方式帮助项目建立了边界，但继续按每个小任务进行多 Agent 轮转会带来明显成本：

- 手动切换对话和复制提示词成本高。
- 不同 Agent 重复读取上下文，token 消耗过快。
- 文档深度开始超过比赛当前阶段需要。
- 个人开发者的主要风险已经从“流程失控”转向“比赛功能深度和演示效果不足”。

因此后续开发采用轻量个人敏捷模式：保留当前代码架构和关键文档资产，降低多 Agent 协作流程重量。

## 2. 总体原则

1. 保留代码架构，不推翻现有 `FastAPI`、`React`、service / adapter / orchestrator、`agent_runs` 等工程资产。
2. 降低协作流程，不再对每个小任务强制执行 Requirement -> Architect -> Implementation -> Review -> State 的完整轮转。
3. 以比赛交付风险划分阶段，优先补齐 A3 赛题要求中的真实 AI 能力、资源类型、多模态展示、画像构建和演示效果。
4. 文档只服务三类目标：比赛提交、关键决策记录、当前阶段同步。
5. 日常开发以 Builder 自审为主，独立 Reviewer 只在高风险能力、阶段验收和合并前介入。
6. 每轮开发产出必须是可演示增量，而不是单纯流程文档增量。
7. 每次提交应围绕一个清晰功能增量或阶段成果，避免混入无关重构。

## 3. 简化后的角色模式

### Builder

Builder 是日常主开发角色，负责：

- 理解当前阶段目标。
- 实现代码和必要的轻量开发文档。
- 运行相关测试和本地主流程验证。
- 做自审并修复明显问题。
- 输出变更说明、测试结果和残余风险。

Builder 每轮结束前必须给出简短自审：

```text
Self-review:
- Tests run:
- Main user flow checked:
- Risky changes:
- API/schema changed: Yes/No
- Hardcoded demo risk: Yes/No
- Known gaps:
- Ready for commit: Yes/No
```

### Reviewer

Reviewer 不再每轮必需，只在以下场景介入：

- 引入真实 LLM、RAG、数据库迁移、部署脚本等高风险能力。
- 修改 API schema、数据库模型或核心架构边界。
- 连续两次修复同一问题失败。
- 一个阶段完成后准备合并或提交。
- 准备比赛演示和提交材料前。

Reviewer 输出应保持短格式：

```text
Conclusion: Pass / Fix before merge / Blocking
Tests:
Blocking issues:
Important risks:
Optional improvements:
```

### Architect / Requirement

Architect 和 Requirement 不再参与日常小任务，只在以下情况启用：

- 比赛要求或产品范围发生变化。
- 需要新增或修改架构决策。
- 引入新技术栈、切换数据库、切换向量库或改动 Agent 编排方案。
- 需要重新冻结阶段范围或演示主线。

## 4. 开发阶段划分

### Phase 1: 比赛要求对齐与主线冻结

目标：把 A3 官网要求转化为当前项目的比赛交付范围。

主要工作：

- 固化 A3 赛题关键要求。
- 明确当前项目符合项和差距项。
- 冻结演示课程为数据结构。
- 冻结演示主线：画像 -> 学习路径 -> 资源生成 -> Tutor -> Quiz -> Evaluator -> Agent trace。
- 明确必做功能、加分功能和暂不做功能。

退出标准：

- 形成轻量比赛对齐文档。
- 后续开发只补比赛差距，不扩展无关功能。

### Phase 2: 核心智能能力完善

目标：让项目从可运行 MVP 骨架升级为更贴合 A3 要求的 AI 学习系统。

主要工作：

- 修复并稳定真实 LLM Tutor 接入。
- 实现对话式学习画像构建，画像不少于 6 个维度。
- 实现真实 RAG 最小闭环：文档解析、chunking、embedding / vector search、来源引用。
- 将资源生成扩展到至少 5 类：讲解文档、练习题、思维导图、拓展阅读、代码实操案例；视频/动画可先做脚本或分镜。
- 增强学习效果评估，输出薄弱点、资源建议和下一步学习调整。

退出标准：

- 至少一个核心 Agent 使用真实 LLM，且保留 fallback。
- Tutor 或 Resource 能基于资料来源生成内容。
- 资源类型达到比赛要求的 5 类。
- 学生画像满足不少于 6 个维度。
- 主学习闭环可以完整演示。

### Phase 3: 演示体验优化

目标：让评委能直观看懂系统价值和 Multi-Agent 协作亮点。

主要工作：

- 优化前端主流程和页面文案。
- 将 Agent trace 展示为清晰时间线或流程视图。
- 展示每个 Agent 的输入摘要、输出摘要、决策依据和资料来源。
- 增加 loading、error、fallback、空状态提示。
- 增强多模态资源卡片展示。

退出标准：

- 不看代码也能完成 7 分钟演示。
- 页面清楚体现个性化、多智能体、资源生成和学习反馈。
- 常见失败情况不导致页面崩溃。

### Phase 4: 稳定性与交付

目标：保证项目能稳定运行、复现和提交。

主要工作：

- 一键启动和一键验证。
- demo data 重置和环境配置说明。
- 关键 API 和前端主流程 smoke test。
- 依赖、开源协议和 AI 工具使用说明。
- 本地演示不依赖不可控步骤；无 API key 时仍可 fallback。

退出标准：

- 新环境可按 README 跑起项目。
- 默认验证脚本通过。
- 演示路径稳定可复现。

### Phase 5: 比赛材料

目标：把系统包装成可提交、可讲清楚的比赛作品。

主要工作：

- 7 分钟演示脚本。
- PPT 大纲与核心页面截图。
- 系统开发说明书。
- 测试说明书。
- AI Coding 工具使用说明。
- 创新点和赛题要求对应表。

退出标准：

- PPT 能讲清楚价值、技术路线、创新点和效果。
- 演示视频能完整展示主流程。
- 文档满足比赛提交要求。

## 5. 后续执行节奏

推荐每轮开发遵循：

```text
选一个可演示目标
-> Builder 实现
-> Builder 自测和自审
-> 修复明显问题
-> 必要时 Reviewer 复核
-> commit
```

日常不再强制维护复杂状态流转。只有阶段完成、重大风险、准备合并或比赛提交前，才进行更正式的 Review 和状态归档。

## 6. 当前建议

当前应优先进入 Phase 1 的轻量补齐，然后快速转入 Phase 2：

1. 固化 A3 比赛要求对齐文档。
2. 继续修复和稳定真实 LLM Tutor。
3. 实现对话式画像构建和 6 维画像。
4. 扩展 5 类资源生成。
5. 再推进真实 RAG 最小闭环和演示优化。
